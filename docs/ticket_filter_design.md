# 티켓 필터 확장 설계

정리일: 2026-10-12. 상태: 1단계 구현·검증 완료, 2단계 초안 구현·검증 완료.

이 문서는 대화 기록 없이 이어서 구현할 수 있도록 두 단계의 범위, UI, 조건 의미와 검증 기준을 정리한다. 제품 요구사항은 [REQUIREMENTS.md](../REQUIREMENTS.md), 진척도는 [IMPLEMENTATION_ROADMAP.md](../IMPLEMENTATION_ROADMAP.md), 결정은 [UI-034~UI-040](decisions/ui-search-and-notifications.md)와 [DB-027~DB-030](decisions/database-and-data-lifecycle.md)을 따른다.

## 1. 작업 순서와 현재 상태

1. 복합 조건과 필터 생성기 UI를 구현하고 TicketFilter v1 schema·호환 로직·저장 데이터를 제거한다.
2. 1단계를 완료한 뒤 날짜와 담당자·생성자의 동적 기준값을 구현한다.

현재 코드는 TicketFilter v2 조건 트리와 필드 추가형 UI를 사용한다. v1 schema artifact·평면 입력 경로는 제거했다. 동적 값은 TicketFilter v4 계약과 요청별 Resolver로 연결했다. Alembic `20261011_0010`의 v1 정리는 임시 DB에서 검증했으며 실제 사용 DB에는 아직 적용하지 않았다.

사용자는 유지할 v1 저장 필터가 없고, 남아 있어도 테스트 데이터이므로 삭제해도 된다고 확인했다. v1 reader, converter, dual-read나 기존 평면 조건의 호환 adapter를 만들지 않는다. 제거 범위는 티켓 필터에 한정하며 본문·이력·보고서 등의 다른 v1 계약 및 과거 migration 이력을 삭제하지 않는다.

## 2. 1단계 — 복합 조건 구조

- 새 TicketFilter 계약은 v2를 기준으로 조건 트리를 정의한다. 개별 조건은 허용된 필드·연산자·typed 값으로, 그룹은 AND 또는 OR와 하위 조건으로 구성한다. NOT은 조건 또는 그룹 결과를 반전한다.
- 정렬과 페이지 크기는 조건 트리 밖의 조회 설정으로 유지하고 현재 페이지 번호는 저장하지 않는다.
- 같은 필드를 여러 번 사용하고 서로 다른 필드·그룹을 OR로 연결할 수 있다. 담당자 지정과 미지정도 OR로 조합할 수 있다.
- 개별 조건의 부정은 `다음 중 하나가 아님`, `포함하지 않음` 등 필드에 맞는 연산자로 표현하고, 그룹은 `이 그룹 제외 NOT`으로 표현한다.
- 조건은 참·거짓으로 판정한다. 담당자 A 조건은 미지정에 대해 거짓이며 그 NOT은 참이다. SQL NULL의 UNKNOWN이 결과를 누락시키지 않도록 변환한다.
- 최상위에 조건이 없으면 전체 조회다. 빈 하위 그룹과 값이 필요한 연산자의 빈 값은 적용·저장을 거부한다. `미지정`·`미설정`처럼 값이 필요 없는 연산자는 별도로 허용한다.
- 서버가 필드·연산자·값 타입·참조와 전체 크기·조건 개수·중첩 깊이를 검증한다. 임의 SQL·코드·JQL을 입력받지 않는다.

지원 예시:

```text
(담당자 = A AND 상태 = 진행중)
OR
(담당자 미지정 AND 중요도 = Blocker)
```

미지정을 제외한 다른 담당자만 조회하려면 `담당자 지정됨 AND NOT(담당자 = A)`를 사용한다.

## 3. 1단계 — 필요한 필드만 추가하는 UI

처음부터 모든 필드의 입력창을 펼치지 않는다. 초기 조건 영역에는 `필터 추가`, `적용`, `초기화`를 제공하고 정렬·표시 개수는 별도로 둔다. 개인·공유, 목록·칸반은 하나의 편집기를 사용하며 별도 기본/고급 편집기를 중복 구현하지 않는다.

`필터 추가`의 Dropdown에서 필드를 선택하면 `필드 → 연산자 → 값 → 삭제` 조건 행이 생긴다. 필드를 바꾸면 입력 타입과 허용 연산자를 함께 바꾼다. 연산자에 값이 필요 없으면 값 입력창은 숨긴다.

| 필드 | 입력 방식 |
|---|---|
| 키·제목 검색 | Text 입력 |
| 유형·상태·중요도 | 복수 선택 |
| 생성자·담당자 | 검색 가능한 사용자 복수 선택 |
| Epic 및 하위·직접 상위 | 키·제목으로 검색하는 티켓 선택 |
| 생성일·수정일·마감일 | 고정 Date 또는 시작·종료 Date |

Epic 조건은 Epic 자체와 하위 Task·Subtask를 포함하고 직접 상위 조건은 직속 자식만 대상으로 하는 기존 의미를 유지한다. 여러 Epic 등을 조합할 때는 조건을 OR로 묶을 수 있다. 1단계에서 날짜와 사용자는 고정값만 사용한다.

최상위는 `모두 만족 AND`가 기본이며 `하나 이상 만족 OR`로 변경할 수 있다. `그룹 추가`를 사용한 경우에만 하위 그룹을 표시한다. 그룹은 테두리와 들여쓰기로 구분하고 AND/OR 선택·NOT·삭제를 제공한다. 접을 수 있는 읽기 전용 요약은 괄호 범위를 명시한다.

```text
[하나 이상 만족 OR ▾]
  그룹 1 — [모두 만족 AND ▾]
    담당자 [다음 중 하나 ▾] [A, B ▾] [삭제]
    상태   [다음 중 하나 ▾] [진행중 ▾] [삭제]
  그룹 2 — [모두 만족 AND ▾]
    담당자 [미지정 ▾] [삭제]
    중요도 [다음 중 하나 ▾] [Blocker ▾] [삭제]
[필터 추가 ▾] [그룹 추가] [적용] [초기화]
```

저장 UI는 개인·공유 생성 입력창을 각각 상시 노출하지 않는다. 적용 후 `필터 저장`에서 이름과 개인/프로젝트 공유 범위를 선택한다. 불러오기는 개인/공유로 구분한 하나의 선택창으로 제공하고 조건을 편집기에 복원한다. 색상 외에도 범위명으로 공개 범위를 식별한다.

불러온 필터의 이름·범위와 편집 여부를 표시한다. 마지막으로 적용한 조건만 저장·덮어쓰고 미적용 편집이 있음을 명확히 안내한다. 이름 변경·덮어쓰기·삭제를 유지하며 다른 탭의 수정은 기존 updated_at 검사로 보호한다.

## 4. 공통 조회·저장 경계

- API·Web 입력, 저장·불러오기와 URL 모두 새 조건 트리를 손실 없이 전달한다. 저장 필터를 다시 평면 필드로 풀어내지 않는다.
- 목록·count·칸반이 같은 검증과 SQLAlchemy 조건 변환기를 사용한다. URL은 새로고침·링크 공유·페이지 이동·인라인 상세·목록↔칸반·drag 성공/충돌 후 재조회에서 조건을 보존한다.
- 프로젝트 접근·휴지통 제외 조건은 사용자 조건 트리 밖에서 항상 AND로 강제한다. OR/NOT으로 권한 범위나 삭제 제외를 반전할 수 없다.
- 칸반은 일치하는 Task·Subtask만 카드로 표시하고 미일치 조상은 계층 식별에만 사용한다. 상태 열과 필터 밖 의존성 검증, 기존 보드 순서·페이지 미분할 정책을 유지한다.
- IAM-017·IAM-018의 개인 소유권·공유 관리 권한·게스트·비활성 프로젝트·시스템 관리자 override 정책을 유지한다. 편집기에서 공유를 선택해도 서버가 관리 권한을 재검증한다.
- CSRF·same-origin, 중복 이름, optimistic locking, no-op과 감사 rollback 규칙을 유지한다. 진단·감사 context에 필터 이름·검색 내용·조건 원문을 넣지 않는다.
- saved_filters의 JSON definition과 schema_version 저장 공간을 우선 재사용한다. 기존 v1 데이터 정리는 Alembic `20261011_0010`에서 한 번 수행한다. upgrade는 v1 row만 삭제하고 version 기본값을 2로 바꾸며 downgrade는 v2 row를 삭제하고 기본값 1을 복원한다. 삭제된 row는 자동 복구하지 않는다.

## 5. 2단계 — 동적 기준값

대상은 생성일·수정일·마감일의 날짜 기준과 생성자·담당자의 `현재 사용자`다. 고정값도 계속 선택할 수 있다. 새 값 구조에는 고정값과 동적 규칙을 구분하고, 계약 변경 시 schema version을 명시한다.

- 날짜는 Asia/Seoul의 달력 날짜를 기준으로 오늘과 오늘에서 일정 기간 이전의 경계, 이번/지난 working week를 제공한다.
- working week는 월요일~금요일 전체다. 공휴일을 제외하지 않고 외부 Calendar를 연동하지 않는다. 주말에 적용해도 해당 달력 주의 월~금이며, 이번 주의 미래 금요일까지 포함한다.
- timestamp의 working week 범위는 월요일 00:00 이상·토요일 00:00 미만이고, Date 범위는 월요일~금요일이다. 고정 Date 입력도 기존 날짜 전체 포함 규칙을 유지한다.
- `오늘부터 1주 전까지`의 최근 기간과 `오늘 기준 1주 전 이전`의 오래된 항목 조회는 별도 의미로 표현한다. 화면의 문구와 연산자로 방향·경계를 구분한다.
- `현재 사용자`는 필터 저장자가 아니라 적용 요청의 로그인 사용자다. 공용 필터를 A와 B가 각각 적용하면 각자의 ID로 조회한다. 이 값은 업무 데이터 쓰기 권한을 부여하지 않는다.
- 저장에는 `이번 working week`, `현재 사용자` 등의 규칙을 보존하며 날짜·사용자 ID로 고정하지 않는다. 요청마다 같은 기준 시각·사용자를 한 번 결정해 목록·count·칸반에 동일하게 적용한다.
- 적용 결과에 실제 날짜 범위·사용자를 표시한다. 다시 적용·새로고침하면 기준을 다시 계산하고 URL 공유도 받는 사용자의 현재 기준으로 해석한다.

공용 `내 이슈`는 기존 대시보드 정의(UI-013)를 재사용한다. 종료 상태 제외는 자동으로 넣지 않고 별도 상태 조건으로 조합한다.

```text
담당자 = 현재 사용자
OR
(담당자 미지정 AND 생성자 = 현재 사용자)
```

`내가 생성한 이슈`는 생성자 조건만 사용한다. `수정일 = 이번 working week`는 현재 마지막 수정일이 해당 기간인 티켓을 찾는다. 기간 내 모든 변경을 재구성하는 변경 이력 조회·주간보고 수집기·LLM 실행은 두 단계에 포함하지 않는다.

## 6. 단계별 완료 기준

1단계는 다음 조건을 모두 만족해야 완료다.

- 서로 다른 필드의 OR, 중첩 AND/OR, 조건·그룹 NOT, 동일 필드 반복, 복수 사용자와 미지정 조합을 검증한다.
- 빈 값·그룹, 잘못된 연산자·타입·참조, 조건 규모 제한과 NULL의 부정 의미를 검증한다.
- v1 schema artifact·reader·converter·호환 입력 경로를 제거하고 새 계약의 예시·테스트·개인/공유 안내를 갱신한다. 정리 절차는 v1 저장 필터만 제거하고 다른 업무 데이터를 보존한다.
- 개인·공유 lifecycle, 권한·CSRF·stale·감사 rollback과 목록/count·칸반 일관성을 회귀 검증한다.
- 실제 Browser에서 필드별 입력 전환·추가·삭제·중첩·요약·저장/복원과 URL·화면 전환·drag 재조회 보존을 검증한다.

2단계는 다음 조건을 모두 만족해야 완료다.

- 고정/동적 값 선택과 규칙 저장·재적용, 공용 필터의 사용자별 결과를 검증한다.
- working week의 월/금/주말·주/월/연도 경계와 Asia/Seoul 날짜 경계를 검증하고 목록/count가 같은 기준을 사용함을 확인한다.
- 실제 Browser에서 동적 조건을 저장·불러오고 실제 해석값을 확인한다. 시간·사용자 변경 후에도 규칙이 보존되어야 한다.

Label·Ad-hoc 필터, 전문 검색과 별도 보고서 기능은 이번 두 단계의 범위에 추가하지 않는다.

## 7. 독립 날짜 경계 확장

- 이번/지난주의 월~일을 단일 기준일로 선택하고 기간의 시작·종료에도 각각 지정한다. 고정 날짜·오늘·N일 전후와 혼합할 수 있으며 양 끝 날짜를 포함한다. UI-040·DB-030을 따른다.

위 항목은 두 단계의 범위를 바꾸는 미확정 요구사항이 아니라 구현 세부사항이며 확정 시 같은 작업에서 결정 문서를 갱신한다.

## 8. 확정된 1단계 계약 (v2 이력)

- [JSON Schema](contracts/ticket-filter.v2.schema.json)와 [고정값 예시](contracts/ticket-filter.v2.example.ko.json)를 게시한다. 조건은 kind=condition, field, operator, values, negated이며 그룹은 kind=group, operator=AND/OR, children, negated다.
- JSON은 UTF-8 최대 4 KiB, group 포함 node 60개, root 포함 깊이 5, 조건당 선택값 30개다. URI encoding한 filter 값은 최대 12 KiB다(UI-036·UI-037).
- 선택 필드의 연산자는 in/not_in, 검색은 contains/not_contains, 날짜는 on/before/after/between이다. assignee·parent·due_date만 is_empty/is_not_empty를 허용한다.
- on/between은 양 끝 날짜 전체를 포함하고 before/after는 선택일 전체를 제외한다. 값은 엄격한 정수 ID 또는 YYYY-MM-DD이며 Date 경계는 0002-01-01~9998-12-31이다.
- API·Web은 `filter=<v2 JSON>`만 조건 입력으로 받는다. 구형 q/type/status 등의 평면 필터, 알 수 없는 parameter와 중복 query는 400이다. page·selected·created·loaded_scope·loaded_id는 화면 상태로 별도 유지한다.
- 저장 관리 중 미적용 편집이 있으면 생성·덮어쓰기를 비활성화한다. 이름 변경·삭제는 선택한 row의 updated_at과 관리 권한을 검사한다.
- migration의 제거 범위와 로그·downgrade는 DB-028을 따른다. 현재 실제 운영 데이터 적용은 별도 실행 전이며 기동 시마다 정리하는 서비스는 없다.

## 9. 1단계 검증 결과

2026-10-11 Windows 전체 pytest 487개가 실제 Edge Browser 시나리오를 포함해 통과했다. 임시 Docker 환경의 Linux 전체 pytest는 461개 통과·14개 skip이며 Ruff도 통과했다. JavaScript 문법·문서 링크·결정 ID·diff 검사와 데이터가 있는 migration upgrade/downgrade를 검증했다. Browser에서는 필드별 입력, 중첩·NOT·복수 선택, 개인/공유 저장·복원과 미적용 편집, 목록·칸반·drag 재조회 시 조건 보존을 확인했다. 실제 사용 DB migration과 배포는 실행하지 않았으며 2단계 구현은 시작하지 않았다.

## 10. 2단계 초안

상대 기간의 입력·경계, v3 규칙, 요청별 해석과 v2 보존 migration은 [동적 기준값](dynamic_filter_criteria.md)을 따른다. 주 요일과 독립 시작·종료 기준 입력을 추가했으며 확장 구현·회귀 검증을 완료했다.

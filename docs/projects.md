# 프로젝트·참여자 관리

확정된 프로젝트 역할은 **프로젝트 게스트**, **프로젝트 사용자**, **프로젝트 관리자**다. 게스트는 읽기 전용이고 담당자가 될 수 없으며, 사용자는 creator·assignee와 무관하게 프로젝트의 모든 티켓 업무를 수행한다. 관리자는 이에 더해 프로젝트와 참여자·역할을 관리한다. 시스템 관리자는 전체 프로젝트와 사용자·조직·보존·정리 작업을 관리하며 비참여 프로젝트 접근은 감사한다.

현재 구현은 프로젝트 생성·조회·기본 정보와 활성 상태 변경, 사용자별 즐겨찾기, 세 역할의 저장·참여자 추가·기존 참여자의 역할 변경과 제거, 마지막 관리자 보호와 티켓 권한 단순화까지 연결되어 있다.

## 화면과 API

| 화면 / API | 동작 |
|---|---|
| `/projects`, `GET /api/projects` | 명시적으로 참여한 프로젝트 목록 |
| `POST /projects/{key}/favorite` | 내 프로젝트의 사용자별 즐겨찾기 설정·해제 |
| `/admin/projects`, `GET/POST /api/admin/projects` | 시스템 관리자 전용 전체 목록·생성 |
| `/projects/{key}`, `/projects/{key}/settings`, `GET /api/projects/{key}` | 기본 정보와 참여자 조회 |
| `POST /projects/{key}/settings`, `PATCH /api/projects/{key}` | 이름·설명·활성 상태 변경과 재활성화 |
| `/projects/{key}/members`, `GET/POST /api/projects/{key}/members` | 참여자 조회·등록 |
| `POST /projects/{key}/members/{member_id}/role`, `PATCH /api/projects/{key}/members/{member_id}` | 기존 참여자 역할 변경 |
| `POST /projects/{key}/members/{member_id}/remove`, `DELETE /api/projects/{key}/members/{member_id}` | 기존 참여자 제거 |
| `GET /api/admin/project-candidates` | 생성 시 최초 관리자 후보 검색 |
| `GET /api/projects/{key}/candidates` | 프로젝트 관리자용 미참여 활성 사용자 검색 |

목록은 `q`, `page`, `page_size`를 받으며 이름·ID 순서로 정렬한다. 페이지 크기는 10·20·50이며 기본값은 외부 pagination 설정을 따른다. 후보 API는 `q`로 로그인 ID·표시 이름을 검색하고 이름·ID 순서로 최대 50명을 반환한다. 화면에서는 `candidate_q`로 같은 검색을 수행한다.

내 프로젝트 카드의 별표는 회색의 미설정 상태와 노란색의 설정 상태를 오간다. 즐겨찾기는 `ProjectMember`에 사용자별로 저장하며, 설정된 프로젝트는 현재 목록의 검색·페이지와 무관하게 모든 로그인 화면의 왼쪽 `내 프로젝트` 아래에 이름순으로 표시한다. 명시적으로 참여하지 않은 시스템 관리자 override 프로젝트는 즐겨찾기할 수 없고 참여가 제거되면 즐겨찾기도 함께 제거된다.

내 프로젝트 카드의 `프로젝트 열기`와 왼쪽 navigation의 즐겨찾기 프로젝트는 해당 프로젝트의 티켓 목록으로 이동한다. 시스템 관리자의 전체 프로젝트 관리 목록은 설정과 참여자 관리가 목적인 프로젝트 root 연결을 유지한다. 공통 navigation은 topbar의 toggle button으로 접고 펼치며 같은 browser에서 선택 상태를 유지한다.

생성 입력은 `key`, `name`, `administrator_id`, 선택적 `description`이다. 키는 공백 제거·대문자 정규화 후 `[A-Z][A-Z0-9]{1,31}` 형식으로 저장하며 변경하지 않는다. 프로젝트와 최초 관리자 등록은 원자적으로 수행하고 생성 응답은 `201`과 `id`, `key`다. 생성자는 별도로 지정하지 않았다면 참여자로 추가되지 않는다.

수정 입력은 `name`, `description`, `is_active` 중 하나 이상이며 명시한 필드만 변경한다. 프로젝트 key는 수정 입력에 포함하지 않는다. 프로젝트 관리자와 시스템 관리자는 프로젝트를 비활성화·재활성화할 수 있으며 비활성화는 참여자와 업무 데이터를 변경하지 않고 기존 조회 권한을 유지한다. 같은 값 요청은 no-op이다.

현재 참여자 등록 입력은 `user_id`, 선택적 `role`이며 `PROJECT_USER`가 기본값이고 `PROJECT_GUEST`, `PROJECT_ADMIN`도 지정할 수 있다. 조직은 등록 조건이 아니며, 비활성 사용자나 비활성 프로젝트의 신규 등록은 차단한다. 중복 등록으로 기존 역할을 덮어쓰지 않는다. 프로젝트 게스트는 티켓과 보드를 조회할 수 있지만 티켓 생성·수정·상태 전이는 할 수 없고 담당자 후보에서도 제외한다.

역할 변경 입력은 `role`만 허용한다. 비활성 프로젝트 또는 비활성 참여자는 동일 역할·권한 축소만 허용하고 권한 확대는 차단한다. 마지막 프로젝트 관리자는 하위 역할로 변경하거나 제거할 수 없다. 휴지통 밖의 미완료 티켓을 담당하는 참여자는 게스트로 변경하거나 제거할 수 없으며, 완료·취소·휴지통 티켓의 담당자는 이력으로 유지한다. 해당 티켓의 재개·복구 시 담당자가 현재 활성 프로젝트 사용자 또는 관리자인지 다시 검사한다.

## 권한과 감사

- 인증되지 않은 API 요청은 401, 비밀번호 변경 미완료·역할 부족은 403이다. 미참여 일반 사용자의 프로젝트 조회·등록은 존재하지 않는 프로젝트와 같은 404를 반환한다.
- HTML과 API 쓰기는 동일한 서비스와 입력 계약을 사용한다. same-origin과 CSRF를 검사하며 API는 `/api/auth/csrf`의 토큰을 `X-CSRF-Token`으로 보낸다.
- 시스템 관리자도 내 프로젝트에서는 명시적 참여 목록만 본다. 전체 프로젝트 목록·직접 접근으로 운영 접근할 수 있으며, 참여 권한으로 허용되지 않는 list/read/write/manage 접근은 `project.override_access`로 남긴다.
- `project.created`, `project.updated`, `project.deactivated`, `project.reactivated`, `project.member_added`, `project.member_role_changed`, `project.member_removed`는 데이터 변경과 같은 transaction에 저장한다. 참여자 감사에는 대상 프로젝트·사용자·변경 전후 역할을 기록한다. 감사 저장 실패는 변경을 롤백하거나 조회 결과 반환을 중단한다. 같은 프로젝트 정보·역할 요청은 변경 감사와 성공 시스템 로그를 남기지 않지만 시스템 관리자 override 감사는 유지한다.
- SQLite 쓰기 잠금 이후 현재 시스템 역할·프로젝트 역할과 프로젝트 상태를 재검사한다. 시스템 로그에는 안정 식별자와 작업·오류 코드만 기록한다.

## 남은 범위

프로젝트 key는 생성 후 변경하지 않는다. 생성 시 최초 관리자를 반드시 지정하고 역할 변경·제거에서도 마지막 관리자를 보호하므로 관리자 없는 프로젝트가 생성되지 않는다.

티켓 생성·조회·편집·상태 전이·관계 관리, 칸반 상태 이동, 계층 단위 휴지통 이동·복구, 일반 첨부파일과 본문 이미지 업로드·조회는 실제 프로젝트 접근 권한과 DB 데이터를 사용한다. 휴지통·첨부파일 삭제와 영구 정리 명령 및 scheduler 연계는 아직 준비 중이다. 내 작업 대시보드는 명시적으로 참여한 프로젝트의 실제 티켓과 미확인 멘션만 조회한다.

현재 Alembic head는 프로젝트 참여자별 즐겨찾기를 추가한 `20260929_0006`이다. `20260923_0003`을 되돌리면 게스트를 쓰기 가능한 사용자로 승격하지 않고 게스트 membership을 제거하므로 운영 downgrade 전 백업과 역할 정리가 필요하다. PostgreSQL 잠금·macOS 실환경과 정밀 화면 배치 검증은 별도로 남아 있다.

이 문서에 기술한 프로젝트 기능을 포함한 현재 브랜치는 Windows Python 환경에서 전체 pytest 339개와 Ruff·JavaScript 문법 및 diff 검사를 통과했다.
